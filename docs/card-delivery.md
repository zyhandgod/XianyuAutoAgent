# 本地卡密发货

入口是 `cards.py` / `start-local.command`，不运行原来的 AI 入口 `main.py`。
不需要模型 API Key、服务器、域名或开放公网端口；电脑需保持联网且不休眠。

## 本地管理后台

双击 `start-admin.command`，打开 http://127.0.0.1:8765 。后台只监听本机，不发布到互联网。
发货服务默认停止；聊天模拟已停止，后台不提供聊天关键词发卡模式。

## 登录与多用户隔离

首次打开时由使用者设置管理员用户名和密码，无默认密码。用户名为3–32位字母、数字、点、
下划线或短横线，密码10–128位。初始化只允许一次；之后由管理员在“账号管理”创建成员。
普通成员不能创建或停用其他账号。管理员管理登录账号，也只能访问自己的业务数据。

每个后台用户有独立 Cookie、商品、卡密、订单去重记录、日志和发货进程。
服务端从登录会话确定用户，不接受浏览器传入的用户ID来切换数据空间。
切换用户、退出或会话过期后会清空页面业务内容；同一浏览器各标签共用登录，
同时测试两个账号请使用不同浏览器或无痕窗口。

账号密码使用独立随机盐的 scrypt 哈希，登录会话为8小时，原始会话令牌不写入数据库，
浏览器使用 HttpOnly、SameSite=Strict Cookie。修改密码会撤销所有已登录会话；
停用成员也会撤销其会话并停止其后台发货进程。退出登录本身不会停止已启用的发货服务，
需要停止时先在运行设置中操作。后台进程退出仍会停止全部由它管理的发货进程。

首次管理员初始化时，原根目录 `.env` 和 `data/cards.db` 的快照仅归入首个管理员，
其他用户从空白工作空间开始。用户工作空间为 `data/users/<内部用户ID>/`，
各自配置位于 `.env`，库存位于 `data/cards.db`，日志位于 `data/service.log`。
账号、会话及闲鱼账号归属保存在共享 `data/auth.db`，备份时需保留整个 `data/` 目录。
多用户模式优先通过后台管理；若人工恢复需运行CLI，应指定该用户的 `CARD_WORKSPACE`，
不要混用旧根目录数据库。

同一闲鱼卖家账号永久归属首次绑定它的后台用户，不能在其他用户中重新绑定。
用户可以切换自己绑定过的不同闲鱼账号，原来的订单去重记录仍在同一工作空间保留。
这避免跨用户转移卖家账号后丢失历史记录、重复发卡；不同用户的不同卖家账号可同时运行。

目前仍是仅本机访问的版本；各自电脑远程使用需另行部署并配置 HTTPS，不会自动开放公网端口。

- 商品与卡密：添加商品链接/ID和名称，按商品导入卡密；库存弹窗显示完整卡密内容。未分配卡密可修改、停用或删除；已分配卡密保留可点击的“重新启用”，点击后释放原订单分配、恢复为可分配库存；多卡订单会整单释放，修改和删除仍受保护。
- 发货记录：分开显示卡密发送、平台发货和待人工核对状态；失败可只重试平台发货。
- 运行设置：保存 Cookie（不回显）、查看日志、启动演练观察或真实发货、停止服务。

启用真实发货前要求启用商品并有真实库存；后台不接受 MOCK/DEMO 测试卡密。
暂停商品后不再分配新卡，但已发卡的订单仍会完成平台发货。已分配的卡密不能直接修改或删除；确认需要回收时，在库存弹窗点击“重新启用”，该订单的整批卡密会恢复为可分配库存。
关闭浏览器标签不会停止服务；请在运行设置中停止服务，或退出后台所在终端。
后台进程退出会停止它启动的发货进程，异常退出由子进程检测父进程消失后退出。
其他终端启动的进程显示为外部进程，需在原终端停止，不会误报停止或允许切换账号。

## 配置及使用

在项目目录使用 `.venv/bin/python`。本机环境已安装；重建时使用 Python 3.12：

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-cards.txt
```

将 `.env.cards.example` 中的设置填入 `.env`，填写卖家账号的完整 `COOKIES_STR`。
默认 `CARD_DRY_RUN=true`，演练模式只查询订单并提示，不消耗库存、不创建会话、不发送卡密。
普通聊天、关键词及买家发送“已付款”均不会触发发货。

## 真实聊天中的 MOCK 测试

用户明确要求的聊天模拟使用独立入口：双击 `start-mock.command`，或执行
`.venv/bin/python cards.py mock-chat`。它会连接真实闲鱼账号并发送**测试消息**，
与 `CARD_DRY_RUN` 控制的付款演练不同。另一个买家账号在聊天中发送完整的 `已支付`，
会收到“模拟发货，仅供测试”的 `MOCK-TEST-...` 卡密，内容明确说明不可使用且不代表核实付款。
无需付款、商品ID或导入卡密；不查询订单，不操作 `data/cards.db`，不更改平台发货状态。
模拟记录只保存在 `data/mock-cards.db`，命令不允许将模拟数据库改到其他路径。
同一条消息重放/重连不会重复回复；新发一条关键词可再次测试。仅处理程序启动后5分钟内的消息，
卖家自己发送的关键词不触发。`Ctrl+C` 停止，与正式服务不可在同目录同时启动。
本模式验证消息收发，**不能验证真实付款识别**；正式发货依然使用 `cards.py run`。

无需凭据即可先试离线演示：双击 `demo-local.command`，或执行
`.venv/bin/python cards.py demo`。它使用临时数据库和虚构订单，演示首次发卡、
重复订单跳过、重启去重、按购买数量整单分配、库存不足和库存耗尽，不连接任何远端服务。

1. 把卡密粘贴到本地 `data/cards-import.txt`，UTF-8，一行一个，不添加标题或注释。
2. 从商品链接取得 `id` 或 `itemId`，按商品导入（下面的商品ID必须替换）：

```sh
.venv/bin/python cards.py import --item-id 你的商品ID --file data/cards-import.txt
.venv/bin/python cards.py stock
.venv/bin/python cards.py run
```

未填 Cookie 时可以用全局参数 `--seller-id` 指定 Cookie 中的 unb 做离线导入和库存查看，
但真实运行一定使用 Cookie 认证的账号。不要把卡密或 Cookie 发到聊天。
相同账号重复导入同一卡密会跳过，即使换了商品也不会重复入库。
卡密按商品隔离。真实订单读取卖家订单里的 `priceVO.buyNum`：购买数量为 1 至 100 时，一次性锁定对应数量的卡密并合并成一条消息发送；库存不足、数量缺失或异常时整单不发，不能按聊天内容猜测数量。不同 SKU 需要单独商品。

先在演练模式用一笔新付款订单确认接口权限和订单识别。停止程序，把 `.env` 的
`CARD_DRY_RUN=false` 后再次启动，才会实际发卡。演练不会把订单记为已发，切换真实模式后
仍会处理演练期间识别到、且当前仍待发货的订单。

## 付款识别与边界

每30秒查询卖家订单列表，仅认接口中的精确状态 `待发货` 或 `pending_ship`，
且必须有真实订单号、商品ID、买家ID及可解析的付款时间。账号需要有卖家中心订单接口权限。
接口或状态格式变化时停止该轮处理，不根据聊天或红色通知猜测付款。
发卡前用订单号再次查询，订单状态、商品、买家及付款时间必须仍完全一致。
仅处理此数据库内该账号首次启动后付款的订单，避免初次启动补发此前人工处理过的订单。
首次启动时间保存在 `data/cards.db`，重启保留；已运行之后离线期间的新付款可在下次扫描补发。
最多扫描100条订单，超过范围本轮拒绝处理并提示；暂无大规模历史订单补偿。

注册和同步遵循原项目的单向握手顺序，并用请求ID匹配的心跳回执检查连接。
会话和发送接口要求匹配请求ID的成功回执。卡密发送回执仅表示接口接收，
不证明买家已读。真实模式在卡密消息获确认后，将平台发货任务与卡密发送结果一起持久化，
再次核对订单身份、付款时间和退款标记，调用 `mtop.taobao.idle.logistic.consign.dummy` 确认无需物流发货，
回查订单为待收货/已发货/交易成功后才标记平台发货完成。演练观察模式不会修改订单。
发货接口超时只重查/重试平台状态，不重发或重新分配卡密，最多5轮后转人工核对。
可在后台发货记录中恢复重试，或执行 `cards.py retry-shipping --order-id 订单号`。
当前协议参考公开项目实现。2026-10-17 已使用本账号只读验证消息登录、卖家订单查询以及
长连接心跳，且关键词触发的 MOCK 消息收发已实测通过。无需物流发货尚未对真实订单调用，
仍需真实商品库存和一笔新付款订单完成正式发货链路联调，
不能把接口连通或模拟测试当作真实发卡成功。
订单核验与消息发送是两个独立操作，不能阻止两者之间发生的极短时间退款状态变化。

## 去重及故障处理

SQLite 事务在发送前持久化卡密分配，订单号和卡密各有唯一约束。
单个账号同时只允许一个本地发货进程。重复通知、重复轮询和重启不会自动发第二张。
网络超时或发送中断会记录 `uncertain`；进程突然终止可能留下 `sending`。
这两种情况均不自动重试、不退回库存，因为买家可能已经收到。

用 `stock` 查看待核对订单，到闲鱼聊天中人工确认。如果需要取回原分配卡密，可在本机执行：

```sh
.venv/bin/python cards.py reveal --order-id 你的订单号
```

确认聊天里已经收到（或人工把原卡密发给同一买家）后：

```sh
.venv/bin/python cards.py confirm-sent --order-id 你的订单号
```

该命令只标记本地记录，不发消息也不修改平台订单。库存弹窗中的“重新启用”用于释放本地订单分配并恢复整批库存，不会撤回已经发送给买家的消息，也不会修改平台订单。
缺库存不建分配记录，补库存后下轮重查订单再尝试。消息发送超时会保留整批卡密为不确定状态，不自动拆分、补发或重新分配。
`data/`、`.env` 均忽略提交；数据库和启动进程创建的文件限制为本机当前用户访问。
数据库和原始导入文本包含明文卡密，请保管并备份。**不要删除或更换库存数据库后继续真实发货**，
否则会丢失去重记录。演练测试使用临时数据库，不写入真实库存。

## 本地验证

```sh
.venv/bin/python -m unittest discover -s tests -v
```

验证库存并发分配、重复订单、重启去重、缺库存、错误状态、不确定回执保留、
演练不耗卡、付款后再核验、RPC回执关联。全部测试均为本地模拟，不连接闲鱼。
测试涵盖付款模式和模拟模式；模拟不能读取正式库存，读取消息与等待发送回执分别运行。
测量命令（需开发工具 `coverage`）：

```sh
.venv/bin/python -m coverage run --source=card_store,card_orders,card_agent,card_mock,cards,admin -m unittest discover -s tests
.venv/bin/python -m coverage report -m
```
